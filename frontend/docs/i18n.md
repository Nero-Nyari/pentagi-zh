# Frontend i18n

The UI ships in English and Simplified Chinese. It carries its own translator —
no i18n library — because the whole of what this app needs is a dictionary, a
lookup with `{placeholder}` interpolation, and one plural rule. [`react-i18next`]
would have added two dependencies and a provider hierarchy for the same result.

[`react-i18next`]: https://react.i18next.com

## Layout

```
src/lib/i18n/
    types.ts            Language, TranslationKey, Translator
    detect.ts           Picks 'zh'/'en' from navigator.languages
    translator.ts       createTranslator(dictionary) — interpolation + plurals
    runtime.ts          Translator for code that cannot call a hook
    agent-types.ts      camelCase agent key → role-name key
    dictionaries/
        index.ts        Record<Language, Dictionary>
        en/index.ts     Compiles every namespace into `Dictionary`
        en/<ns>.ts      Flat, dot-named keys
        zh/<ns>.ts      Same keys, `satisfies Dictionary`
```

`en/index.ts` is the source of truth: it composes the namespaces and exports
`Dictionary = typeof en`, so `TranslationKey` is literally the union of every
English key. `zh/index.ts` is checked with `satisfies Dictionary`, which means a
missing or misspelled Chinese key is a **compile error**, not a runtime
fallback to English.

Namespaces are a filing convention, not a runtime concept — every dictionary is
flattened into one table. Current namespaces: `common`, `nav`, `ui`, `shared`,
`auth`, `dashboard`, `flows`, `report`, `settings`, `knowledges`, `templates`,
`resources`, `errors`.

## Using it

```tsx
import { useTranslation } from '@/hooks/use-translation';

function Empty({ count }: { count: number }) {
    const { t } = useTranslation();

    return <p>{t('shared.fileManager.items', { count })}</p>;
}
```

`useTranslation()` never throws. Without a provider it returns a working English
translator, which is what lets the ~200 existing component tests render in
isolation without wrapping everything in `<LanguageProvider>`.

Outside React — the axios interceptors are the only current case — use
`runtimeT` from `src/lib/i18n/runtime.ts`. It starts on English and
`LanguageProvider` repoints it whenever the language changes.

## Keys

- Flat, dot-named, namespace-prefixed: `settings.providers.form.name`.
- Interpolation is `{name}`, passed as the second argument.
- Plurals use an `_one` sibling selected from `values.count`:

  ```ts
  'x.tasks': '{count} tasks',
  'x.tasks_one': '{count} task',
  ```

  Chinese defines both keys with the same value; the mechanism is shared so the
  two dictionaries stay structurally identical.

- **Module-level constants must not hold copy.** A list of menu items, columns,
  or tabs stores a `TranslationKey` and the component calls `t(...)` at render —
  see `titleKey` in `src/components/layouts/settings/settings-sidebar.tsx`.
- **Zod messages** are built by a `createXxxSchema(t)` factory; the module also
  exports the English-bound instance so non-React importers keep working. See
  `src/pages/settings/settings-provider.tsx`.

## What gets translated

Translated: buttons, headings, labels, table headers, `placeholder`,
`aria-label`, `title`, empty and loading states, errors, confirmations, toasts,
validation messages, select options, status badges, the document title.

Left alone: code comments, `console`/`Log` output, GraphQL fields and enum
values, routes, CSS class names, the product name, and anything that arrives
over the wire (flow titles, model names, agent names from the API). Values from
the API go into templates as interpolations, never through the dictionary.

Two deliberate exceptions worth knowing about:

- **Preset templates** (`src/pages/templates/template.tsx`) stay in English. The
  title and the body are one unit, and the body is a prompt payload the agent
  reads — a translated title over an English body would be worse than either.
- **Dates, durations and numbers** are still formatted with `date-fns`' `enUS`
  and `Intl`'s `en-US`. Localizing them is a separate change: it needs the
  language threaded into `src/lib/utils/format.ts` and its many call sites.

## Adding a key

1. Add it to the English namespace file.
2. Add the same key to the Chinese file. Skipping this fails `tsc`.
3. Run `pnpm test src/lib/i18n` — `dictionaries.test.ts` asserts that both
   dictionaries have identical key sets, identical `{placeholder}` sets per key,
   and no empty values.

## Adding a language

1. Extend the `Language` union in `src/lib/i18n/types.ts`.
2. Copy `dictionaries/en/` to `dictionaries/<code>/` and translate the values.
3. Wire it into `dictionaries/index.ts` — the `Record<Language, Dictionary>`
   there fails to compile until you do.
4. Add the name to `language.name.*` and the short form to `language.short.*`.
5. Extend `detectLanguage` in `src/lib/i18n/detect.ts`, and the pre-mount script
   in `index.html` that stamps `<html lang>` before React boots.

The language toggle is a two-state flip (`en` ⇄ `zh`); with a third language it
needs to become a menu.

## Persistence and first paint

The choice is stored under the `language` key through
`src/lib/local-storage.ts` (Zod-validated). First visit falls back to
`navigator.languages`. `index.html` repeats that rule in a small inline script
so the first paint already has the right `<html lang>`; `LanguageProvider` takes
over on mount.

`<html translate="no">` stays: browser auto-translation rewrites text nodes React
owns, which desyncs the DOM.
